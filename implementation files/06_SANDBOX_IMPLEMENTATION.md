# Sandbox Implementation Guide — Controlled Patch Execution

## Goal
Apply an approved patch to a disposable demo workspace in an isolated environment, then make that environment available to the test runner.

## Ownership
Primary owner: testing/demo-app member, guided and reviewed by the backend lead. This module is security-sensitive; the lead must review it.

## Critical safety rule
Never allow an AI-generated patch or command to execute directly on a developer's Windows host. Do not mount the host filesystem broadly into a container. Do not mount the Docker socket inside the container. Do not run privileged containers.

## MVP scope
Support only:
- One known demo application.
- A fixed allowlist of editable files.
- One selected patch format.
- One trusted application method.
- A fixed test command configured by the application, not generated by the LLM.

Do not support arbitrary repositories or arbitrary shell commands in the first version.

## Proposed flow
1. Backend confirms the patch exists and is approved.
2. Patch validator checks file paths, patch format, and size limits.
3. Sandbox service creates a fresh workspace from a known demo image or clean source snapshot.
4. Validated patch is applied inside the isolated workspace.
5. Sandbox reports application success/failure and a workspace/run identifier.
6. Verifier runs the trusted test command in the sandbox.
7. Sandbox is destroyed after evidence/results are collected.

## Required restrictions
Apply appropriate Docker restrictions:
- Non-root user.
- No privileged mode.
- CPU, memory, process, and execution-time limits.
- No host credentials or secrets.
- No broad host directory mounts.
- Read-only base filesystem where practical, with a narrowly scoped writable workspace.
- Network disabled or tightly restricted unless specifically required.
- No Docker socket mounted into the workload.
- Output size limits and timeout handling.

Exact Docker flags and isolation settings must be reviewed and tested on the team's environment. Docker alone is not a complete security boundary for hostile code; keep the MVP limited to trusted demo code and controlled patches.

## Patch validation
Before application:
- Resolve and normalize the target path.
- Reject absolute paths and path traversal (`..`).
- Reject files outside the allowlist.
- Limit patch size and number of changed files.
- Reject unexpected binary files and unsupported patch formats.
- Do not trust a file path or command supplied by the LLM.
- Verify the patch belongs to the incident and approval record.

## Execution result schema
Return structured data:
- `run_id`
- `patch_id`
- `status` (`created`, `applying`, `applied`, `failed`, `timed_out`)
- `changed_files`
- `exit_code`, if applicable
- `stdout_summary`
- `stderr_summary`
- `started_at`
- `completed_at`
- `error`

Do not return full sensitive environment information in logs.

## Rollback language
Do not claim rollback exists unless it is implemented and tested. For the MVP, the safer approach is to use a fresh disposable workspace per run and discard it after execution. This naturally prevents a failed demo patch from changing the developer's source checkout.

## Implementation steps
1. Create a minimal demo Docker image.
2. Confirm the demo image runs without privileged mode.
3. Implement a patch allowlist and path validator.
4. Implement a sandbox runner with fixed commands.
5. Add timeouts and resource limits.
6. Return structured execution results.
7. Connect only after human approval.
8. Add tests for path traversal, invalid patch, timeout, failed application, and successful application.
9. Ensure cleanup occurs after each run.

## Definition of done
- [ ] Patch execution requires a recorded approval.
- [ ] Only allowlisted paths can be changed.
- [ ] No arbitrary LLM-provided shell command is executed.
- [ ] Execution occurs in a restricted disposable environment.
- [ ] Timeout and failure are reported accurately.
- [ ] Workspace cleanup is verified.
- [ ] Host project files remain unchanged.
